# Benchmark red-team audit: timing methodology

Scope: `paper_submission_revision/` (sections 00, 01, 04, 07, 08, 09, 10, 12; tables/*.tex), the kernels in `src/kernels/`, the harnesses in `scripts/`, and the artifacts in `results/`. No GPU job was run for this audit. Every number below was recomputed from the released JSON with numpy/stdlib.

Estimator definitions used throughout:
- **min ratio**: min over all samples of the numerator, divided by the min over the dense set {dense_fused, dense_triton, dense_tuned} (or {sdpa, flex_dense, dense_tuned} in precision.json). This matches `scripts/make_revision_tables.py:54-57`.
- **median ratio**: the numerator's median divided by the smallest dense median. The paper calls this the "paired median". It is a ratio of two separately computed marginal medians. A true paired estimator, the median over repetitions of the per-round ratio, cannot be computed because per-sample latencies are not stored (see V5).
- **run range**: for i = 1..3, the numerator's run-i median divided by the smallest dense run-i median. Both come from the same timed block, so this is the only genuinely paired quantity in the artifacts. The prescore artifacts store only `inter_run_spread_pct`, so the range across sweeps (prescore / prescore_repeat / prescore_selectors) is given instead.

**Is the dense baseline the strongest available?**
- fp32: in the precision sweep the authors' tuned Triton kernel beats SDPA (cutlass mem-efficient, built for sm_80) and FlexAttention at every fp32 configuration. It reaches 30–47% of a measured SGEMM rate (`tables/autotune.tex`). No flash or cuDNN backend exists for fp32 (sdpa_backend_probe.json: only mem_efficient and math). So the baseline is the best of what was tested, but it is not demonstrated to be near the device limit. The paper says so.
- bf16: FlashAttention is excluded by the self-mask (probe `by_mask.additive_float`). Unmasked flash is 2.5× faster than mem-efficient at N=512 (0.0388 vs 0.0989 ms). cuDNN is listed as available with the mask but the dispatcher picks mem_efficient, and cuDNN was never forced. FlexAttention bf16 (0.0242 ms at d16, N=512) beats unmasked flash anyway, so in practice the bf16 baseline is strong. MINOR gap: try `SDPBackend.CUDNN_ATTENTION` explicitly.
- TF32: the "library" entry is not TF32 at all. sdpa tf32 deviation is 1.7e-6, identical to fp32 (precision.json), so mem-efficient ignores `allow_tf32`. The TF32 baseline is flex or ours. This is harmless, but "library" in TF32 rows means fp32.

## 5. Is the fused crossover algorithmic, implementation-specific or hardware-specific?

**IMPLEMENTATION-SPECIFIC, with a hardware-path (precision) dependence. It is not algorithmic.**
- The algorithmic bound for score-then-select is at most a 2× arithmetic reduction (Prop. 1). The observed advantage (ratio 0.67–0.94) appears only where the best dense kernel reaches 30–47% of a measured SGEMM rate in fp32-IEEE, i.e. both kernels run on the FMA path, far from the machine limit.
- It vanishes from N=384 upward once dense uses tensor cores (TF32/bf16, minima). Under the median it survives marginally at one bf16 configuration (V6), so even that boundary is soft.
- It exists only at k=1, where the softmax is degenerate and the "sparse" kernel is a hard argmax-copy. At k=2 it holds at one configuration (d=32, N=512: 0.90–0.92, stable across autotune, its repeat and precision).
- Both kernels are hand-written and one author's. The sparse search space is truncated by an analytic filter (V10), and the main sweep uses an untuned sparse kernel. Changing either kernel, or adding a streaming exact top-k, could move the boundary in either direction.
